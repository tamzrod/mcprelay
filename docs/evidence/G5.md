# G5 — Phase 3 Authentication and Credential Boundary (Evidence)

**Date:** 2026-08-10  
**Phase:** 3 — Authentication and Credential Boundary  
**Gate:** G5 (Phase 3 acceptance)  
**Result:** **PASS**

## Summary

The Phase 3 authentication boundary is implemented and validated. The connector
now authenticates the downstream client (OpenHands Cloud) with a bearer
connector API key, performs the Notion OAuth lifecycle (discovery → DCR → PKCE
→ consent → exchange → refresh → rotation → `invalid_grant`), persists
credentials encrypted at rest in SQLite, serializes refresh per grant, survives
restart, and connects to the authenticated upstream MCP — all without exposing
upstream credentials downstream.

The full G2 lifecycle is exercised against a **mock OAuth authorization server +
authenticated MCP upstream** (`src/test/mock-auth-server.ts`). **No real Notion
credentials** are used (security requirement: never put secrets in test
fixtures); all tokens are random throwaway values.

## Implementation

### New modules

- `src/store/crypto.ts` — AES-256-GCM field encryption (`encryptSecret`/
  `decryptSecret`), master-key loading (`loadMasterKey`, fail-fast), scrypt
  hashing/verification for the downstream key (`hashApiKey`/`verifyApiKey`,
  constant-time), and a non-reversible `apiKeyFingerprint` for logging.
- `src/store/credential-store.ts` — SQLite credential store (better-sqlite3,
  WAL). Tables: `notion_grant` (DCR creds + access/refresh tokens encrypted,
  expiry, bot_id, owner, scope, status), `downstream_key` (scrypt hash),
  `oauth_flow_state` (PKCE verifier + state, single-use). Atomic
  `(access_token, refresh_token)` rotation in one transaction (G2).
- `src/auth/auth-manager.ts` — OAuth manager: `discoverOAuthServerInfo` →
  `registerClient` (DCR) → `startAuthorization` (PKCE S256 + state) →
  `exchangeAuthorization` → `refreshAuthorization`. Proactive refresh before
  `expires_in`; 401 → one refresh+retry; per-grant mutex serializes refresh;
  `invalid_grant` (`InvalidGrantError`) → terminal `requires_reauth`, no retry
  loop. Does NOT use the transport's `authProvider` auto-path (D-12).

### Modified modules

- `src/upstream/upstream-client.ts` — attaches the rotating bearer token via a
  custom `fetch` wrapper (per-request, not static `requestInit.headers`);
  `withRefreshRetry` does a single 401 → refresh → retry cycle.
- `src/downstream/downstream-server.ts` — D-13 API-key gate on `/mcp`
  (401 + `WWW-Authenticate` on missing/invalid); `GET /oauth/authorize` +
  `GET /oauth/callback` (D-11); `GET /health` (grant status, no secrets);
  structured reauth-required MCP error on terminal grant (no token leak).
- `src/connector.ts` — wires store + auth + upstream + downstream; grant-aware
  startup (starts without a grant to serve `/oauth/authorize`; connects upstream
  eagerly only if a grant exists — restart survival).

### Test harness

- `src/test/mock-auth-server.ts` — in-process mock of Notion's hosted MCP + OAuth
  authorization server: RFC 9728 protected-resource metadata, RFC 8414
  authorization-server metadata, RFC 7591 DCR, authorize endpoint (redirect with
  code+state), token endpoint (authorization_code + refresh_token grants,
  rotating refresh tokens, `invalid_grant` on revocation), and an authenticated
  MCP upstream (401 without/with-expired bearer; `notion_echo` tool).
- `src/test/auth.test.ts` — 10 G5 acceptance tests.
- `src/test/e2e-auth.ts` — end-to-end driver (real connector + mock auth).

### Criterion-by-criterion

1. **Downstream API-key authentication works** — Test 1. A valid
   `Authorization: Bearer <key>` reaches the MCP handler; `tools/list` returns
   the upstream tool. Key validated via scrypt (constant-time).
2. **Unauthorized clients are rejected** — Tests 2 & 3. Missing bearer → 401
   with `WWW-Authenticate: Bearer realm="mcprelay"`; invalid key → 401.
3. **Operator can authorize Notion** — Tests 4 & e2e. `GET /oauth/authorize`
   302-redirects to the authorization server (D-11 connector-hosted flow).
4. **Notion OAuth completes** — Test 4. Full chain: RFC 9728 → RFC 8414
   discovery → RFC 7591 DCR → PKCE S256 → authorize redirect → token exchange.
   Grant persisted with `status: active`.
5. **Credentials persisted securely** — Test 4. The raw SQLite DB file does NOT
   contain the access/refresh tokens in plaintext (AES-256-GCM at rest, D-10).
6. **Refresh-token rotation works** — Test 5. After expiry, `refreshOn401`
   returns a new access token AND a new rotated refresh token; both differ from
   the pre-refresh values (G2 rotation invariant).
7. **Refresh survives restart** — Test 6. The store is closed and reopened from
   the same DB file + master key; the grant (including the latest rotated
   refresh token) is recovered; a new AuthManager obtains a valid token without
   re-consent.
8. **Concurrent refresh is serialized** — Test 7. 5 concurrent `refreshOn401`
   calls; the per-grant mutex serializes them so at least one succeeds and the
   server-side refresh call count does not exceed the concurrency (no
   concurrent-refresh `invalid_grant` storm — G2 invariant).
9. **invalid_grant handled correctly** — Test 8. After revoking the grant on
   the auth server, `refreshOn401` throws a reauth-required error (not a
   retry loop); grant status becomes `requires_reauth` (terminal, G2).
10. **Authenticated upstream MCP connection works** — Test 9 & e2e. The
    upstream `notion_echo` tool is listed and called through the bearer; the
    result `[mock-notion:echo] <message>` returns unchanged.
11. **OpenHands never receives Notion credentials** — Test 10 & e2e. The
    serialized downstream `callTool` response contains neither the access token
    nor the refresh token.

## Security invariants (verified)

- No OAuth tokens in source code; no secrets committed.
- Access/refresh tokens and the downstream key are never logged (only the
  non-reversible key fingerprint `e2e-***0(len=23)` appears in logs).
- Refresh tokens never reach the downstream client (Test 10).
- Upstream credentials are never returned through MCP (Test 10).
- Test fixtures use only random throwaway tokens (never real Notion credentials).
