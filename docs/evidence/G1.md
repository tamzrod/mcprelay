# G1 Evidence — OpenHands Cloud compatibility (bearer `api_key`)

- **Gate:** G1 — OpenHands Cloud compatibility
- **Question:** Can OpenHands Cloud consume a remote MCP endpoint authenticated
  with a bearer API key, with no custom headers and no interactive OAuth?
- **Outcome:** **PASS**
- **Validated:** 2026-08-10
- **Roadmap ref:** [ROADMAP.md](../ROADMAP.md) Phase 1 · [DECISIONS.md](../DECISIONS.md) gate-status row G1

> This is an experiment record, not connector implementation. No test fixture,
> secret, or temporary server is committed to the repository. Credentials used
> during the experiment were random, throwaway, and have been destroyed.

## Environment (OpenHands Cloud)

- **API:** OpenHands Cloud V1 app server, `https://app.all-hands.dev/api/v1/...`, Bearer auth with an account API key.
- **MCP transport:** Streamable HTTP (SHTTP).
- **MCP config location:** Stored user settings, `agent_settings.mcp_config`.
- **MCP config shape accepted:** the SDK-shaped dict, e.g.:

  ```json
  "mcp_config": {
    "shttp": { "url": "https://<host>/mcp", "api_key": "<redacted>", "enabled": true }
  }
  ```

- **Settings update mechanism:** `POST /api/v1/settings` with an `agent_settings_diff` payload (deep-merged; the legacy `agent_settings` key is rejected with HTTP 422 `"Use *_diff nested settings payloads instead of legacy keys"`).
- **Server-side normalization:** the supplied `api_key` is persisted as
  `auth: { strategy: "api_key", value: "**********" }` — i.e. OpenHands treats
  `api_key` as a first-class auth strategy distinct from OAuth.
- **Conversation:** started via `POST /api/v1/app-conversations`; the MCP config
  is read from stored settings (a per-conversation `agent_settings.mcp_config`
  override in the start payload was **ignored** — see "Limitations").

## Test (temporary MCP server)

A throwaway Streamable HTTP MCP server was run on the workspace runtime's
public ingress (work host, port 12000). It:

- exposed MCP at `POST /mcp` using the official `mcp` Python SDK (`MCPServer.streamable_http_app`);
- required `Authorization: Bearer <G1_TEST_KEY>` on every request and returned HTTP 401 otherwise;
- exposed one trivial tool, `g1_test()` → `"G1_OK: bearer-authenticated MCP tool call succeeded"`;
- logged each request's method/path, the redacted `Authorization` summary, the
  negotiated `mcp-protocol-version`, the `mcp-session-id`, and the `User-Agent`.

The test key was a random, non-secret value generated at run time and destroyed
after the experiment. DNS-rebinding protection in the SDK was disabled for the
fixture only (so the public ingress hostname was accepted); this is a
server-side transport-security setting of the throwaway fixture and does not
bear on the G1 auth question. **No fixture code is committed.**

## Evidence

### Test-server request log (OpenHands Cloud client, `User-Agent: python-httpx/0.28.1`)

All requests carried `Authorization: Bearer <key>` and were accepted. No
custom headers. No OAuth. The complete MCP lifecycle was observed:

```
request POST   /mcp  auth_ok=true  auth=Bearer g***P(len=32)  proto=            ua=python-httpx/0.28.1  sess=-
request POST   /mcp  auth_ok=true  auth=Bearer g***P(len=32)  proto=2025-11-25  ua=python-httpx/0.28.1  sess=e3d1e089
request GET    /mcp  auth_ok=true  auth=Bearer g***P(len=32)  proto=2025-11-25  ua=python-httpx/0.28.1  sess=e3d1e089
request POST   /mcp  auth_ok=true  auth=Bearer g***P(len=32)  proto=2025-11-25  ua=python-httpx/0.28.1  sess=e3d1e089   (tools/list)
request POST   /mcp  auth_ok=true  auth=Bearer g***P(len=32)  proto=2025-11-25  ua=python-httpx/0.28.1  sess=e3d1e089   (tools/call)
tool_call      tool=g1_test  args={}
```

The distinct User-Agent (`python-httpx/0.28.1`) and distinct session id prove
these requests came from the OpenHands Cloud runtime, not the local probe
(`python-httpx2/2.10.0`), which validated the fixture beforehand.

## Finding

G1 is satisfied. OpenHands Cloud can act as an MCP **client** to a remote
Streamable HTTP MCP server using only the `api_key` field, which it transmits
as an `Authorization: Bearer <key>` header, with no custom headers and no
interactive OAuth. This validates the proposed **downstream** leg of the MCP
Connector architecture (D-05): the connector can expose a single bearer-API-key
SHTTP endpoint to OpenHands Cloud. The architecture/roadmap assumptions that
G1 guarded are valid; no architectural change is required.

### Limitations observed (do not block G1)

- **Per-conversation MCP override is ignored.** Passing
  `agent_settings.mcp_config` inside the `POST /api/v1/app-conversations` body
  was accepted (HTTP 202) but **silently ignored** — the agent reported no MCP
  tools. MCP config for a Cloud conversation must be set in the **stored user
  settings** (`agent_settings_diff` → `mcp_config`) before starting the
  conversation. This is an operational constraint on how OpenHands Cloud picks
  up MCP servers, not a G1 auth failure. The connector's downstream interface
  (a bearer-key SHTTP URL) is unaffected; only the *config delivery path*
  differs.
- **Settings diff API, not legacy keys.** `POST /api/v1/settings` accepts
  `agent_settings_diff` (deep-merge) and rejects the legacy `agent_settings`
  key with HTTP 422. (Documented in OpenHands `AGENTS.md`.)
- **Tool-name prefixing.** OpenHands exposes remote tools under a
  transport-prefixed name (e.g. `shttp_g1_test`), not the raw upstream name.
  The connector design must account for this in its advertised tool names if
  name stability matters; this is a Phase 2+ concern.
- **No long-lived credential behavior tested.** G1 covers only the
  downstream bearer-key connection path. Upstream OAuth (Notion) refresh,
  revocation, and persistence are G2/G5, not G1.
