# G4 — Minimal connector forwards MCP against a mock upstream

- **Gate:** G4 (Phase 2 exit gate, M2)
- **Date:** 2026-08-10
- **Outcome:** **PASS**
- **Maps to:** ROADMAP Phase 2; MILESTONES M2; ARCHITECTURE §2 (downstream
  server, relay, upstream client), §3 (boundaries); DECISIONS D-08 (stateless
  MVP), D-09 (TypeScript/Node.js + `@modelcontextprotocol/sdk`).

## What G4 guards

> Minimal connector successfully forwards MCP capabilities and tool calls against
> a mock upstream. Only after G4 may auth work proceed.

G4 validates the core relay shape end-to-end before any authentication,
credential store, or real upstream is introduced.

## Validated path

```
MCP Client (Streamable HTTP)
        |
        v
MCP Connector  (downstream server :8789/mcp)
        |  relay (transparent forwarding)
        v
MCP Connector  (upstream client)
        |
        v
Mock Upstream  (Streamable HTTP :8788/mcp, tool: g1_test)
```

## Implementation (Phase 2, deliberately small)

- **Language/runtime:** TypeScript on Node.js (D-09).
- **MCP SDK:** official `@modelcontextprotocol/sdk` 1.30.0 — the well-documented
  stable ESM line. Server side: `Server` + `StreamableHTTPServerTransport`.
  Client side: `Client` + `StreamableHTTPClientTransport`.
- **Layout (explicit separation required by Phase 2 spec):**
  - `src/downstream/` — MCP server exposed to clients (Streamable HTTP).
  - `src/upstream/`  — MCP client connected to upstream MCP (Streamable HTTP).
  - `src/relay/`     — request/capability forwarding.
  - `src/test/`      — mock upstream + integration tests + smoke test.
  - `src/connector.ts` — entry point wiring the three layers.
- **Transport:** Streamable HTTP, **stateless** (`sessionIdGenerator:
  undefined`) on both legs — the MVP-allowed path (D-08), confirmed safe for the
  Notion workflow by G1/G2 (no SSE-delivered notifications required for the
  read/update/comment operations).
- **Stateless server pattern:** a fresh `McpServer` per HTTP request (the SDK's
  own `simpleStatelessStreamableHttp` example pattern); the relay/upstream client
  is long-lived and shared across requests.

## What the connector does NOT do (scope respected)

- No OAuth, no credentials, no credential store.
- No Notion connection.
- No multi-user support, no downstream auth beyond a placeholder.
- No multiple upstreams.
- No SSE streaming (stateless only).
- No upstream-specific business logic (verified by review: the relay forwards
  whatever tools the upstream exposes; `tools/list` and `tools/call` are
  generic).

## Known limitations (deliberate Phase 2 scope)

- **Stateless only (D-08):** no `Mcp-Session-Id` issued on either leg; no SSE
  streaming; no resumption. AC-P2-2 (session correlation) is deferred to the
  stateful/SSE phase. This is the MVP-allowed path, not a regression.
- **Single upstream, single long-lived upstream client:** no routing table, no
  lazy reconnect/backoff, no idle reclamation (Phase 6).
- **No structured logging / audit log** beyond console startup lines (Phase 3/6).
- **No health endpoints** (Phase 6).
- **No downstream auth:** the connector accepts all callers (placeholder); real
  downstream `api_key` validation is Phase 3/4 (G1 confirmed the mechanism).
- **Fresh server per request:** simple and correct for the prototype, but not
  tuned for high throughput; revisit when stateful sessions are added.
- **Error handling is minimal:** 500 + JSON-RPC error envelope; no retry,
  backoff, or circuit breaking (Phase 6).

## No architectural problem discovered

No redesign was required. The transparent-relay architecture (ARCHITECTURE
§2/§3, D-06/D-07) held: the connector forwards capabilities and tool calls
without implementing upstream business logic. The stateless Streamable HTTP
path (D-08) is viable for the MVP.
