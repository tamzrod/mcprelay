## The blocker — Notion human consent (OAuth category)

### What was validated against real Notion

The connector's OAuth subsystem (`src/auth/auth-manager.ts`) ran against the
**real** Notion hosted MCP and metadata endpoints — not the mock. Verified:

1. **RFC 9728 protected-resource metadata** — `GET https://mcp.notion.com/.well-known/oauth-protected-resource` → `{"resource":"https://mcp.notion.com","authorization_servers":["https://mcp.notion.com"],...,"resource_name":"Notion MCP (Beta)"}`.
2. **RFC 8414 authorization-server metadata** — `GET https://mcp.notion.com/.well-known/oauth-authorization-server` → `authorization_endpoint: https://mcp.notion.com/authorize`, `token_endpoint: https://mcp.notion.com/token`, `registration_endpoint: https://mcp.notion.com/register` (DCR), `grant_types_supported: [authorization_code, refresh_token, ...]`, `token_endpoint_auth_methods_supported: [..., "none"]` (public client / PKCE).
3. **RFC 7591 Dynamic Client Registration** — the connector registered a real client with Notion and received a real `client_id` (redacted; a public PKCE client identifier, not a secret — `token_endpoint_auth_method: "none"`).
4. **PKCE S256** — a real `code_challenge` + `code_challenge_method=S256` was generated and bound to a persisted `state`.
5. **Authorize redirect** — `GET /oauth/authorize` on the connector → **HTTP 302** to
   `https://mcp.notion.com/authorize?response_type=code&client_id=<real>&code_challenge=<real>&code_challenge_method=S256&redirect_uri=https://work-1-…/oauth/callback&state=<real>`.

Visiting that authorize URL in a browser redirected to
`https://app.notion.com/login` — Notion's real login/consent page. **This is the
human-consent gate.** A human with a Notion account must authenticate and
approve the connector there; Notion then redirects back to the connector's
`/oauth/callback` with an authorization code, which the connector would
exchange (via `exchangeAuthorization`) and persist encrypted. That final step
cannot be completed without a Notion account holder.

### Why this is not an architectural failure

- G2 (PASS) already established this exact behavior: *"Notion hosted MCP is
  OAuth-only, requires a human browser consent, explicitly not
  headless/bearer-auth."* The connector's design (D-11 connector-hosted consent
  flow) is built around this. The code is correct; the missing input is a human
  authorizer.
- The full OAuth lifecycle mechanics (exchange → persist → refresh → rotation →
  `invalid_grant` → restart survival) are validated at G5 against a mock auth
  server that faithfully implements Notion's metadata/DCR/token endpoints. The
  only thing the mock cannot provide is a real Notion account's consent.
- No code change would unblock #7 without a Notion account. This is an
  **operational/credential dependency**, the "OAuth" failure category named in
  the Phase 4 instructions.

### What unblocks G6

An operator with a Notion account performs a one-time consent:

1. Visit `https://work-1-…prod-runtime.all-hands.dev/oauth/authorize` in a
   browser (the deployed connector is live and serving this route).
2. Log in to Notion and approve the connector.
3. Notion redirects to the connector's `/oauth/callback`; the connector
   exchanges the code and persists the encrypted grant.
4. The connector establishes the upstream MCP connection; `tools/list` returns
   Notion's real tools; OpenHands tool calls succeed; restart preserves the
   grant.

No re-deployment or code change is required — the deployed connector already
serves the consent flow against real Notion. The remaining G6 criteria (#7–#9,
#12–#14) are expected to pass once consent is granted; the infrastructural
prerequisites they depend on (#1–#6, #10, #11) are already PASS.

## Consent-attempt failure diagnosis (2026-08-10, second attempt)

### What happened

After the operator reported consent completion, the connector was inspected.
Findings:

- **Health:** `upstream_grant.status = "absent"` — no grant.
- **`notion_grant` table:** 0 rows — no grant persisted.
- **Connector log (timestamped):**
  ```
  2026-08-10T08:48:40.808Z [connector] /oauth/callback failed:
    ReauthRequiredError: OAuth callback state not found or already consumed
    (possible replay/CSRF).
  ```
  The callback **did reach the connector**, but `consumeFlowState(state)` found
  **no matching state** in the encrypted store.

### Timeline (from timestamped logs)

| Time (UTC) | Event |
|---|---|
| 08:02:52 | Connector first boot (startup banner #1) |
| 08:03:56 | A `/oauth/authorize` GET created a flow_state row (state redacted; the URL handed to the operator) |
| 08:17:52 | Container restarted (restart-survival test; startup banner #2) |
| 08:48:40 | **Operator's consent callback reached the connector → FAILED: state not found** |
| 08:53:03 | Reproduction test (correct state + fake code) → `InvalidGrantError: Invalid authorization code format` (state check PASSED, exchange rejected fake code) |

At the time of the failed callback, two flow_state rows existed (one from 08:03
and one from 08:48, both states redacted here). **Neither was consumed** (both
still present after the callback) → the operator's callback state matched
**neither** → the operator used an authorize URL whose state was never stored in
**this** connector's database (a stale URL, or a URL from a different/earlier
connector instance whose flow_state did not survive into this DB).

### Root-cause verification: NOT a code defect

The connector's OAuth state mechanism was independently verified correct:

1. **State persistence:** A fresh `GET /oauth/authorize` returns a 302 whose
   `state` parameter **exactly matches** the row written to `oauth_flow_state`
   (verified by reading the encrypted store: the URL state == the DB state).
   ✓
2. **State consumption:** Hitting `/oauth/callback?code=<fake>&state=<real>`
   with the **correct** state **passed** the state check and proceeded to the
   token-exchange step, which returned `InvalidGrantError: Invalid authorization
   code format` (Notion rejecting the fake code) — the **expected** failure for
   a bad code. The flow_state row was correctly consumed/deleted. ✓
3. **Error discrimination:** The operator's error was
   `state-not-found` (state check); the reproduction's error was
   `invalid-code` (exchange). Different stages → the operator's state never
   matched a stored row. ✓

**Conclusion:** The connector code is correct. The failure is **operational** —
the operator completed Notion consent using an authorize URL whose flow_state
was not present in this connector's database. The most probable cause is a
stale authorize URL (generated before a container restart/redeploy, or opened
from a cached page) whose single-use state was never persisted to (or was
consumed from) the current store.

### Why no workaround was applied

Per the Phase 4 instructions, an actual failure must be documented, not
silently worked around. The fix is **operational, not code**: the operator must
open a **fresh** `/oauth/authorize` URL from the **currently running** connector
(so its state is in the current DB), complete the Notion login + approval, and
let Notion redirect back to the connector's `/oauth/callback`. The deployed
connector already serves this flow correctly against real `mcp.notion.com`.

- (Optional hardening, **not** required for G6 and **not** implemented here:
