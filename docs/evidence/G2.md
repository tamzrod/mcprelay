# G2 Evidence — Notion MCP OAuth Behavior

- **Gate:** G2 — Notion OAuth behavior confirmed
- **Question:** What are the actual OAuth credential lifecycle and failure
  semantics for the Notion MCP service?
- **Outcome:** **PASS** (documentation-established)
- **Validated:** 2026-08-10
- **Roadmap ref:** [ROADMAP.md](../ROADMAP.md) Phase 1 · [DECISIONS.md](../DECISIONS.md) gate-status row G2

> No connector code was written. No live OAuth exchange was performed. This
> gate establishes what the future connector **must** do; it does not
> implement it. No real OAuth credentials were handled or committed.

## Evidence sources (authoritative, in priority order)

1. **Official Notion docs — "Build an MCP client for Notion"**
   `https://developers.notion.com/guides/mcp/build-mcp-client` — the canonical
   guide for third-party clients connecting to Notion's hosted MCP
   (`https://mcp.notion.com/mcp`). Contains the 8-step OAuth flow and an
   explicit "Notion MCP OAuth specifics → Token lifecycle" section. All
   lifecycle facts below are quoted from this page unless noted.
2. **Official Notion docs — "Authorization"**
   `https://developers.notion.com/guides/get-started/authorization` — the
   public-connection OAuth token/refresh endpoints and credential-storage
   guidance (referenced for the refresh request shape and persistence advice).
3. **Official Notion docs — "Connect to Notion MCP"**
   `https://developers.notion.com/guides/mcp/get-started-with-mcp` — confirms
   auth model (OAuth-only, browser-based).
4. **MCP authorization spec alignment** (secondary, for protocol context):
   RFC 9728 Protected Resource Metadata + RFC 8414 Authorization Server
   Metadata + OAuth 2.1 Authorization Code + PKCE (S256) + Dynamic Client
   Registration (RFC 7591). Corroborated by multiple independent technical
   write-ups; used only to frame the discovery/401 mechanics, not for
   Notion-specific values.

A live OAuth experiment was **not** required to establish G2 and was **not**
performed: the official Notion docs explicitly state every lifecycle value the
gate asks for (access-token TTL, refresh-token presence/lifetime, rotation,
`invalid_grant`, restart persistence). Running the browser-based OAuth flow
would require an operator + Notion workspace and would create real-credential
exposure risk, without adding information the authoritative source lacks. A
live confirmation of refresh-rotation and `invalid_grant` behavior is instead
scheduled as a **Phase 3 (G5)** validation target, where the connector itself
exercises the lifecycle.

## Credential lifecycle the future connector must manage

Confirmed from official docs. This is the **specification** the Phase 3
credential subsystem (D-10/D-11) must satisfy:

1. **Bootstrap (once per connection):**
   - Discover authorization-server metadata via the MCP 401/`WWW-Authenticate` →
     `/.well-known/oauth-protected-resource` → `/.well-known/oauth-authorization-server` chain.
   - **Dynamic Client Registration** → obtain and durably persist `client_id` + `client_secret` (public client, PKCE, `token_endpoint_auth_method=none`). Re-registering orphans prior grants, so reuse them. (CIMD is an alternative Notion supports.)
2. **Authorize (operator-in-the-loop, browser-based):**
   - Generate PKCE verifier/challenge (S256); open browser to the authorization endpoint; operator selects workspace and consents; handle the redirect callback; exchange the authorization code for tokens.
   - Persist `access_token`, `refresh_token`, `expires_in`, `bot_id`, `owner`.
3. **Use:** Send `Authorization: Bearer <access_token>` to the upstream MCP. Cache the access token with its real `expires_in`.
4. **Refresh (proactive, before expiry):**
   - Refresh **5–10 minutes before** `expires_in` (access tokens ~8h). `POST` token endpoint with `grant_type=refresh_token`.
   - **Persist the new `refresh_token` atomically** with the new `access_token` (rotation: old token retired).
   - **Serialize refreshes per grant** (mutex/distributed lock) — concurrent refreshes of the same grant cause losers to get `invalid_grant`.
5. **Failure handling:**
   - `invalid_grant` → **terminal**: clear stored tokens, surface a reconnect, do not retry-loop.
   - `temporarily_unavailable` / network errors → retry with backoff.
6. **Restart:** Credentials remain usable after a connector restart **iff** the DCR credentials and the latest rotated `refresh_token` were durably persisted. A crash mid-rotation that loses the new `refresh_token` kills the connection (the old one is retired) → re-authorize.
7. **Periodic reconnection is expected, not exceptional:** 180-day absolute cap (no slide) or 30-day inactivity → `invalid_grant` → re-authorize. The reconnect flow must be easy to reach.

### Security implications for the credential store (feeds D-10)

- Must store: DCR `client_id`/`client_secret`, current `access_token`, latest `refresh_token`, `bot_id`, `owner`/workspace identity.
- Must support **atomic** update of `(access_token, refresh_token)` on each rotation.
- Must enforce **serialized** refresh per grant (locking) to avoid concurrent-refresh `invalid_grant`.
- Must treat `invalid_grant` as terminal and clear the grant.
- Encrypted at rest; isolated per tenant/connection; revocable.
- These upstream OAuth credentials are **never** exposed downstream to the OpenHands sandbox (D-02; verified at G5/G6).

## Limitations / unresolved sub-questions (do not block G2)

- **Access-token TTL observed vs documented.** Official docs say ~8h and "use
  `expires_in`." Some community reports (open-webui discussion, GitHub issue
  #225) describe Notion MCP sessions expiring after ~1 hour and refresh not
  happening proactively. The ~1h observation is **unconfirmed** and may reflect
  a client-side refresh bug or an older lifetime; the authoritative
  build-mcp-client doc states ~8h. **Resolution:** always drive off
  `expires_in` (never hardcode), and **live-confirm the actual `expires_in`
  and rotation behavior at G5 (Phase 3)** when the connector exercises a real
  grant. Does not block G2 — the *design* (use `expires_in`, refresh early,
  rotate atomically) is correct under either value.
- **Scopes.** Notion MCP scopes (e.g. read/write) were noted in client
  examples but the exact scope set and its effect on the documentation-workflow
  tool surface is a **G3** concern, not G2.
- **Exact token-endpoint URLs / `WWW-Authenticate` shape** are discoverable at
  runtime via metadata; the connector will fetch them rather than hardcode.
  Not a G2 blocker.

## Finding

G2 is satisfied. The Notion hosted MCP uses **OAuth 2.0 Authorization Code +
PKCE with Dynamic Client Registration**, is **browser-consent-based and
OAuth-only** (no upstream API key), issues **access tokens (~8h, use
`expires_in`) + rotating refresh tokens** (180-day absolute non-sliding cap or
30-day inactivity), rotates the refresh token on every refresh, returns
**`invalid_grant`** (terminal) on expiry/revocation/concurrent-refresh, and
requires the connector to **durably persist DCR credentials + the latest rotated
`refresh_token`** and **serialize refreshes per grant**. The architecture
assumptions G2 guarded (D-02 connector-owns-upstream-auth; D-10 credential
store; D-11 operator consent UX) are all confirmed necessary. No
architectural change is required; the credential lifecycle is now specified
sufficiently for Phase 3 design.

### Implications for the connector (recorded for Phase 3)

- The connector **must** implement the upstream OAuth client (DCR + PKCE +
  browser consent + token exchange + refresh + rotation) — it cannot use a
  static key against Notion's hosted MCP.
- The credential store (D-10) **must** support atomic `(access_token,
  refresh_token)` persistence and per-grant serialized refresh.
- The operator consent UX (D-11) **must** be browser-based and
  re-reachable (periodic reconnection is expected).
- A live validation of refresh rotation and `invalid_grant` is a **G5
  (Phase 3)** target, not a Phase 1 requirement.
