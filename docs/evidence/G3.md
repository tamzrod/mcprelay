  `https://mcp.notion.com/mcp`, perform the operations required for the

## Confirmed capability facts

- **Read:** `notion-fetch` retrieves page/database/data-source content by URL or
  ID, returned as enhanced Markdown (agent-friendly). `notion-search` finds
  pages across the workspace. `notion-fetch` with `id: self` returns the
  connected workspace + user identity (useful for labeling a connection).
- **Create:** `notion-create-pages` creates page(s) under a page or database
  parent with title properties and Markdown `content`; supports templates and
  async large-content writes.
- **Update:** `notion-update-page` updates properties and content; markdown
  update supports insert/`replace_content`/`replace_content_range` commands.
  (A changelog note: a past bug that deleted child content under
  `replace_content` modes was fixed — i.e., update is supported and maintained.)
- **Comments read:** `notion-get-comments` lists all comments/discussions on a
  page, including block-level, inline, and resolved threads, with full content.
- **Markdown content model:** Notion exposes an enhanced ("Notion-flavored")
  Markdown surface for read/create/update that the MCP tools wrap — well-suited
  to agent authoring of development documentation.

## Gaps / limitations (do not make the surface INSUFFICIENT for this workflow)

These are documented limitations of the hosted MCP. None of them block the
*stated* workflow (read docs, create/update docs, read comments). They are
recorded because they affect later phases / scope decisions:

- **Block-level surgical edits are absent.** The hosted MCP exposes page-level
  read/create/update (via markdown), **not** individual block CRUD
  (get/update/delete/append block). For development documentation authored as
  markdown pages, page-level update is sufficient; if block-precise edits
  become a hard requirement later, the open-source
  `github.com/makenotion/notion-mcp-server` (22 tools, integration-token auth,
  soft-deprecated) or the Notion REST block API would be needed — an
  ARCHITECTURE.md §4-C alternative, not a G3 failure.
- **File attachments / webhooks** are not in the hosted MCP surface. Not needed
  for the documentation workflow.
- **Advanced data-source querying** (`notion-query-data-sources`,
  `notion-query-meeting-notes`) requires Enterprise + Notion AI plans and may
  return an upgrade prompt on lower plans. Not required for the stated
  workflow (which uses search + fetch + page CRUD + comments).
- **Auth is OAuth-only / browser-consent (G2).** The hosted MCP is not
  headless-API-key. This is a G2 finding, not a G3 tool-surface gap; it is
  already accounted for in the connector's upstream-auth design.
- **Tool surface is not static.** Notion has shipped tool changes
  (consolidations, renames, e.g. `notion-get-user` → `notion-get-users`) and
  may add/remove tools. The connector's transparent-forwarding design (D-06/D-07)
  advertises the mediated intersection of capabilities, so tool churn upstream
  is tolerated rather than hardcoded.

## Finding

G3 is satisfied (**SUFFICIENT**). Notion's hosted MCP at
`https://mcp.notion.com/mcp` exposes, per official documentation, the tools
required for the development-documentation workflow:

- read documentation → `notion-search` + `notion-fetch`;
- create documentation → `notion-create-pages`;
- update documentation → `notion-update-page`;
- read stakeholder comments → `notion-get-comments`.

The surface covers all four required operations. Documented limitations
(block-level editing, files, webhooks, plan-gated querying) do not affect the
stated workflow. No architectural change is required; the ARCHITECTURE.md §4-C
fallback (a separate Notion REST/block adapter or the open-source MCP server)
remains available if block-precise editing becomes a hard requirement later,
but is not needed for the MVP workflow.

### Implications for the connector (recorded for later phases)

- The connector's upstream capability advertisement (D-06) should forward the
  Notion hosted-MCP tool list (search, fetch, create-pages, update-page,
  get-comments, create-comment, …) transparently, intersected with the
  connector's own mediation policy.
- Because Notion uses enhanced Markdown for content, the connector need not
  transform content shapes — it forwards markdown payloads transparently
  (D-07).
- Plan-gated tools (data-source querying, meeting notes) may be absent or
  return upgrade prompts depending on the operator's Notion plan; the connector
  should advertise only what the upstream actually exposes at runtime
  (discovery-driven, not hardcoded).
- Live end-to-end exercise of read/create/update/comments *through the
  connector* is a **G7 (Phase 5)** target; G3 only confirms the upstream
  surface exists and is sufficient.
